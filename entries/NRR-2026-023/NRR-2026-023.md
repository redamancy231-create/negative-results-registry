## 阴性发现 1：二进制大小未达预登记预期

- **预登记预期**：Rust 二进制 < C++ × 1.5
- **实测**：Rust 474.5 KiB / C++ 244.0 KiB = **1.94×**
- **预登记判定**：不符合预期（未做阈值调整）

### 原因分析

未做 LTO、symbol strip 或 codegen-units 调优。归因为"未知"类（按预登记 §8 归因可接受性清单，已诚实声明未定位根因，已列出初步排查方向）。不属于可接受的"编译器差异"搪塞。

### 教训

- Rust 默认 release 构建的二进制尺寸比 C++ pybind11 更大（monomorphization + 静态链接），超过 1.5× 的预期
- 如果二进制尺寸是硬约束，需要提前启用 `strip = true`、`lto = true`、`codegen-units = 1`，并在预登记中明确调优参数
- 不要在没有调优配置的情况下假设 Rust 二进制比 C++ "差不多大"

## 阴性发现 2：预登记预期方向被严重推翻（DTW/standardize/pattern single）

- **预登记 §7 预期**：DTW 单线程"打平到 Rust 稍慢（10% 内）"、standardize"打平"、pattern single"打平到 Rust 稍快"
- **实测**：DTW ratio = 0.29–0.39（Rust 快 2.6–3.5 倍）、standardize ratio = 0.67（Rust 快 50%）、pattern single ratio = 0.53（Rust 快 47%）

### 原因分析

偏离远超预登记预期，且持续出现在多项指标上。已排除算法差异、编译优化级别、计时边界不一致三项可能原因。候选根因（需后续验证）：C++ numpy→std::vector 转换开销、allocator 差异、编译器 auto-vectorization 差异。

### 教训

- 当预期方向和实测结果严重不符时，预登记不能的事并不只是"没猜对"——而是暴露了对 C++ 实现底层开销的理解不足
- 单线程优势 2.6–3.5× 远超任何合理的"编译器差异"范围——说明 C++ 实现中可能存在可优化的路径
- 预登记 §7 的方向预测在跨语言 benchmark 中不应作为先验判断——两个实现的底层差异太大，不能仅凭"同算法"推断性能

## 阴性发现 3：亚微秒指标测量方法失效（cosine 不可判定 + CoV 普遍偏高）

- **预登记预期**：100 次采样足够区分 ±10% 性能差异
- **实测**：cosine (L=19) 双方 median 均为 0 ns（100 ns 量化致不可判定），DTW (L=19) CoV 7.4%，standardize CoV 28.2%
- **预登记判定**：cosine 新增"不可判定"第四类（预登记三类之外），所有核心项 CoV > 5% 按预登记降级为倾向性结论

### 原因分析

`time.perf_counter()` 在 Windows 上的有效分辨率约 100 ns。当被测操作的执行时间接近或低于刻度精度时，计时器量化噪声在 100 次独立采样中无法被充分平均。100 次采样对亚微秒级指标不足，需要循环放大（1,000–10,000 次/轮）再除以次数。

### 教训

- 预登记时没有规定"当 median 低于计时器有效分辨率时"的处理方式——这个方法论漏洞在实验后才暴露
- 100 次采样在毫秒级任务上足够，在亚微秒级任务上不足——但 benchmark 设计时没有分层采样策略
- 6 项核心指标的结论全部被降级为"倾向性"而非"显著结论"——预登记的统计设计让步于测量工具的物理限制

## 阴性发现 4：cupy GPU 余弦在小批量下加速比为负

- **预登记预期**：未预登记（GPU 功能是 Phase 5 后才加的，不在 Phase 4 预登记范围内）
- **实测**：N=100 候选时 GPU 端到端 0.2×（**比 CPU 慢 5 倍**），N=500 时 0.7×，拐点约在 N=1000
- **预登记判定**：不适用（无预登记阈值）

### 原因分析

GPU kernel launch 开销 + NumPy→CuPy 传输在小批量下主导了耗时。RTX 4060 Laptop 的标准 kernel launch latency 约 5-15 µs，PCIe 传输约 5-50 µs，而 100 个 19 维向量的 cupy dot 在 GPU 上只需 ~0.1 µs——传输 + launch 是计算时间的 50-500 倍。

### 教训

- GPU 加速有明确的数据规模下限——低于此下限时"用 GPU"不是中性选择，而是明显劣化
- 小批量 GPU 加速比为负是教科书级事实，但在实际项目中亲眼看到 0.2× 仍然有教育意义
- 对于"给已有 CPU 项目加 GPU 可选后端"的场景，需要在文档中明确 size threshold（本项目的 GPU adapter 文档已标注 N≥1000 推荐）

## 综合教训

1. **预登记不是预测——是暴露盲区**：预登记 §7 的"预期方向"在 4/12 指标上被推翻。这不说明预登记没用，恰恰说明预登记有用——它把"我们先验认为 X"变成了可检验的命题
2. **基准测试的方法论需要分层**：毫秒级（预登记设计够用）、微秒级（需要循环放大）、亚微秒级（需要 Criterion 型统计框架）
3. **跨语言 benchmark 的复杂性被低估**：同样算法、同样数据结构，Rust 和 C++ 在 `std::vector` vs `Vec`、allocator、exception 语义上的差异会累积成显著的性能差异
