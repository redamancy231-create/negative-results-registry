## 实验概述

### 原始假设

> 多轮 LLM 代码审查（跨 5 种后端 + 多维度审查 prompt）应能检测到项目中的功能性 bug——预期覆盖率接近 100%。

### 方法

对 docx-pipeline 项目进行了 5 轮跨模型审查（GPT-5.6-Sol 主审），覆盖代码正确性、配置契约、安全性、文档完整性等维度。事后通过人工端到端测试（目视验证 + Windows Git Bash 真实环境运行）独立检测实际 bug。

### 预期结果

> LLM 审查应捕获全部或几乎全部功能性 bug；遗漏率预期 <10%。

### 实际结果

**LLM 审查（5 轮）完全漏掉了 3 个实际存在的 bug，遗漏率 100%：**

1. **渲染效果 bug**：Mermaid PNG 在 Word 中 ~4× 拉伸——代码审查只看像素数量，看不到 DPI 元数据缺失
2. **默认路径 bug**：裸模板默认值 `output/docx` 无扩展名，"init→convert"完整路径断裂——审查者看单点代码逻辑正确
3. **终端编码 bug**：gh CLI 中文文件名在 Windows Git Bash 下 GBK/UTF-8 转换失败——审查者看不到终端环境

## 解读与反思

### 为什么会失败？

**LLM 审查存在三类系统性盲区，共享一个特征：bug 不出现在源代码的逻辑层面，而出现在相邻工具链的交互契约中。** 渲染效果 bug 需要目视确认最终输出、默认路径 bug 需要端到端走完整流程、终端编码 bug 需要在真实操作系统环境中才能暴露。代码审查——无论多轮多模型——只能回答"代码说了什么"，不能回答"代码在真实环境中做了什么"。

### 学到了什么？

1. **LLM 审查无法替代端到端目视验证**——渲染效果、默认路径、终端编码三类 bug 全部逃脱了 5 轮跨模型审查
2. **三类盲区的共性**：bug 不在源代码逻辑层面，而在相邻工具链的隐式交互契约中
3. **纯代码审查覆盖率 ≠ 真实 bug 检测率**——审查者看到"代码说了什么"，看不到"代码在真实环境中做了什么"
4. **发现成本远高于修复成本**——三个 bug 的修复总计不到 20 行代码，但诊断靠人工端到端测试而非 LLM 审查
