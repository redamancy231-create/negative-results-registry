## Experiment Overview

### Original Hypothesis

> Multi-round LLM code review (across five backends and multidimensional review prompts) should detect functional bugs in the project, with expected coverage close to 100%.

### Method

The docx-pipeline project underwent five rounds of cross-model review (GPT-5.6-Sol as the primary reviewer), covering code correctness, configuration contracts, security, documentation completeness, and other dimensions. Actual bugs were independently detected afterward through manual end-to-end testing (visual verification + execution in a real Windows Git Bash environment).

### Expected Result

> LLM review should catch all or nearly all functional bugs; the expected miss rate was <10%.

### Actual Result

**Five rounds of LLM review completely missed three real bugs, for a 100% miss rate:**

1. **Rendering-output bug**: Mermaid PNGs were stretched by ~4× in Word—code review saw the pixel count but not the missing DPI metadata
2. **Default-path bug**: the bare template default `output/docx` had no extension, breaking the complete “init→convert” path—reviewers saw the single-point code logic as correct
3. **Terminal-encoding bug**: Chinese filenames from the gh CLI failed during GBK/UTF-8 conversion under Windows Git Bash—reviewers could not see the terminal environment

| Sample size | 5 review rounds × 1 project × 3 empirically observed bug classes |

## Interpretation and Reflection

### Why Did It Fail?

**LLM review has three classes of systematic blind spots with one shared feature: the bug does not occur at the source-code logic layer but in the interaction contracts between adjacent tools.** The rendering-output bug required visual confirmation of the final output; the default-path bug required traversing the full end-to-end workflow; and the terminal-encoding bug required a real operating-system environment to surface. Code review—regardless of how many rounds or models are used—can answer only “what the code says,” not “what the code does in the real environment.”

### What Did We Learn?

1. **LLM review cannot replace end-to-end visual verification**—all three classes of bug (rendering output, default paths, and terminal encoding) escaped five rounds of cross-model review
2. **The three blind spots share one feature**: the bugs occur not in source-code logic but in implicit interaction contracts between adjacent tools
3. **Pure code-review coverage ≠ real bug-detection rate**—reviewers see “what the code says,” not “what the code does in the real environment”
4. **Discovery cost far exceeded repair cost**—fixing the three bugs required fewer than 20 lines of code in total, but diagnosis depended on manual end-to-end testing rather than LLM review

## Related

### Did It Succeed Later?

All three bugs were subsequently fixed. The core lesson remains: testing strategy for AI-assisted development must add “runtime-environment end-to-end testing” and cannot rely solely on LLM code review.
