## Experiment Overview

### Original Hypothesis

> Preregistered (CLAUDE.md "PoC decision table": NRR threshold ≥5×, minimum acceptable ≥2×; PLAN.md §9): on an RTX 4060 Laptop GPU (sm_89), the fc accelerator (pybind11 + CUDA bindings, binding level incl. transfer) on the fixed corpus_synth_v1 (T=1218×N=5000×F=12) minimal parameter-scan pipeline (parameter_scan → per-factor rolling_ic → factor_corr + IC merge, verdict_scope EXCLUDING stock_corr) would achieve an end-to-end speedup of ≥5× versus the best free alternative (qgplearn NOT installed → min(numpy 2.4.4, cupy 14.1.1), same data/mask/semantics, including H2D transfer and merge).

### Method

Preregistration anchor: CLAUDE.md PoC decision table (≥5× NRR threshold / ≥2× minimum) and PLAN.md §9. End-to-end (primary criterion): benchmarks/poc4_e2e_v1.py + benchmarks/phase4_bench_v1.py — minimal parameter-scan pipeline, GPU arm via pybind bindings (factor_cuda_pybind/factor_corr_pybind), numpy/cupy arms via benchmarks/backends.py, symmetric reps + Phase 4 fresh round (ARM ORDER ROTATED + UNTIMED WARMUP + thermal sampling + bootstrap CI), best_free=min(numpy,cupy) recorded at runtime, verdict_scope excludes stock_corr; UNIFIED ESTIMATOR = ratio-of-medians (min(med(numpy),med(cupy))/med(gpu), matching committed poc4); DECISION STATISTIC = worst-case min-of-run-medians. Single-op (product-layer supplement): phase4_bench_v1.py binding level vs numpy/cupy, median + bootstrap CI, warm 3 + 20 samples (raw persisted); adapter overhead measured separately. Reproducibility: both corpora verified via corpus_loader_v1 (data_sha256 fail-closed); pipeline outputs bitwise-identical across two runs; G6 evidence self-hash REAL gate (fail-closed non-zero exit); git HEAD pinned + gate provenance envelope (producer commit bound); corpus_real_v1 (N=93) correctness/determinism anchor only. Re-issued fresh after an independent GPT-5.6-Sol review (13 findings) was closed. Evidence: benchmarks/results/phase4_bench_v1.{json,md} + poc4_e2e_v1.json + acceptance_v1.json.

### Expected Result

> If the hypothesis held: F=12 end-to-end speedup ≥5× (vs best-free, incl. transfer and merge); single-op ≥2×. Preregistered failure criteria: <2× → STOP; ≥2× but <5× → record negative result NRR-2026-024.

### Actual Result

E2E F=12 end-to-end speedup 2.895–3.035× (fresh round unified estimator 2.895×; committed poc4_e2e_v1.json 3.035×; cross-run delta 4.6% stable, ratio-of-medians estimator). The ≥2× minimum acceptable was met (PASS-partial); the ≥5× preregistered target was NOT met (hypothesis falsified). Single-op (binding level incl. transfer, corpus_synth_v1 full, vs best-free): factor_corr 13.15× (≥5×, binding level); this round cs_rank 1.59× / parameter_scan 2.28× / rolling_ic 1.99× / stock_corr general 2.31–2.65×. ⚠️ CROSS-SESSION VARIANCE: single-op medians vary substantially across sessions (e.g. rolling_ic observed 1.99×→6.94×, cs_rank 1.59×→3.11×). The claim "all ops below 5× except factor_corr" is NOT made (rolling_ic can exceed 5× across sessions); per-op boundary claims are indicative only; the preregistered decision rests on the stable E2E. Component-level negative surfaced: e2e per-op ic_stack (IC merge) ~0.72× worse than baseline. Adapter overhead: factor_corr adapter vs raw binding +238% (1112.7ms vs 329.2ms, contract-mandated f32→f64 Python upcast); NO specific product-level speedup is claimed (adapter block and best-free baseline are from different measurement blocks; mechanical combination has no structured basis). corpus_real_v1 (N=93) correctness + bitwise-determinism anchor only.

### Why Did It Fail?

The preregistered ≥5× end-to-end target was not met (2.9–3.0×); the ≥2× minimum was met. Attribution is per-mechanism, each labeled CANDIDATE rather than confirmed: ① FP64 hardware ceiling (candidate, no FP32-aggregation confirmatory experiment run) — RTX 4060 Laptop FP64 ≈ FP32/64 may cap the float64 aggregation ops (rolling_ic/factor_corr reductions/stock_corr general), BUT the same-evidence factor_corr (float64) reaches 13.15×, weakening the ceiling as the main cause. ② Launch/transfer/occupancy overhead (candidate) — explains the float32 ops and the product-level transfer cost. ③ Positive control (binding level) proves kernels CAN reach ≥5× — factor_corr 13.15× on the same non-degenerate corpus_synth_v1 panel; below_5x is workload/layer-related, not universal kernel inefficiency. ④ Layer DISCLOSURE (not causation) — the acceptance kernel-resident and current binding-incl-transfer numbers come from different sessions/baselines; no causal claim that kernel-resident overstates user-side is made (the direction is unstable across sessions). ⑤ Adapter Python overhead — the contract-mandated f32→f64 Python upcast (factor_corr +238%) is a product-layer optimization opportunity, not a binding defect; no mechanical product-layer speedup is claimed. Cross-session variance: single-op medians swing widely (rolling_ic 1.99→6.94×); per-op boundary claims are not decision inputs; the decision rests on the stable E2E. Untested alternative explanations (higher-FP64 GPU, FP32 aggregation path, kernel tuning) are labeled UNTESTED HYPOTHESES. Conclusion bounded to RTX 4060 Laptop + fixed corpus + the stock_corr-excluded E2E scope.

### What Did We Learn?

1. The preregistered dual threshold (≥2× minimum / ≥5× target) made 2.9–3.0× an unambiguous verdict: minimum met, target missed → honestly record the negative, never package a documented gap as success.
2. Consumer GPUs (RTX 40-series) have high performance variance — single-op speedups can swing several-fold across sessions (rolling_ic 1.99→6.94×); preregistered decisions must rest on a stable end-to-end criterion, not volatile per-op boundaries.
3. Perf claims must state the LAYER and transfer scope AND the estimator: kernel-resident / binding-incl-transfer / adapter differ; ratio-of-medians vs median-of-ratios give different numbers (3.076 vs 2.895) — preregister a single estimator.
4. "≥5× reachable" must be anchored per mechanism with the positive control layer-limited: binding-level factor_corr 13.15× proves kernels can exceed 5×, but the product adapter's Python upcast is a real overhead (+238%); do not mechanically combine a product-layer speedup.
5. Declare and stick to the E2E adjudication scope before running (verdict_scope excludes stock_corr); surface component-level negatives (ic_stack 0.72×); benchmarks must rotate arm order + untimed warmup + record thermal; gates must be fail-closed with non-zero exit.

## Key Lessons

1. **Dual preregistered threshold made 2.9–3.0× an unambiguous verdict** — minimum met, target missed → honest negative, no success-washing.
2. **Consumer RTX 40-series variance is high** — single-op speedups swing several-fold across sessions; decisions rest on the stable E2E.
3. **Perf claims must state the layer/transfer scope AND a single preregistered estimator** — ratio-of-medians vs median-of-ratios differ (3.076 vs 2.895).
4. **"≥5× reachable" anchored per mechanism, positive control layer-limited** — binding factor_corr 13.15×; adapter Python upcast +238% is real overhead, no mechanical product speedup.
5. **Declare E2E scope upfront; surface component negatives; rotate arm order + untimed warmup + record thermal; fail-closed gates.**
