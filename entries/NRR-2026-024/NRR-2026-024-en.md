## Experiment Overview

### Original Hypothesis

Preregistered (CLAUDE.md "PoC decision table": NRR threshold ≥5×, minimum acceptable ≥2×; PLAN.md §9): on an RTX 4060 Laptop GPU (sm_89), the fc accelerator (pybind11 + CUDA bindings, binding level incl. transfer) on the fixed corpus_synth_v1 (T=1218×N=5000×F=12) minimal parameter-scan pipeline (parameter_scan → per-factor rolling_ic → factor_corr + IC merge, verdict_scope EXCLUDING stock_corr) would achieve an end-to-end speedup of ≥5× versus the best free alternative (qgplearn NOT installed → min(numpy 2.4.4, cupy 14.1.1), same data/mask/semantics, including H2D transfer and merge).

### Method

Preregistration anchor: CLAUDE.md PoC decision table (≥5× NRR threshold / ≥2× minimum) and PLAN.md §9. End-to-end (primary criterion): benchmarks/poc4_e2e_v1.py + benchmarks/phase4_bench_v1.py — minimal parameter-scan pipeline, GPU arm via pybind bindings (factor_cuda_pybind/factor_corr_pybind), numpy/cupy arms via benchmarks/backends.py, symmetric reps + Phase 4 fresh round (ARM ORDER ROTATED + thermal sampling + bootstrap CI), best_free=min(numpy,cupy) recorded at runtime, verdict_scope excludes stock_corr; DECISION STATISTIC = min-of-run-medians (worst case across fresh rounds). Single-op (product-layer supplement): phase4_bench_v1.py binding level (incl. H2D/D2H) vs numpy/cupy, median + bootstrap 95% CI + CV, warm 3 + 20 samples (raw persisted); adapter overhead measured separately (fc adapter vs raw binding). Reproducibility: both corpora verified via corpus_loader_v1 (data_sha256 fail-closed); pipeline outputs bitwise-identical across two runs; G6 evidence self-hash real gate (missing/dirty source FAILs); git HEAD pinned; corpus_real_v1 (N=93) correctness/determinism anchor only. Evidence: benchmarks/results/phase4_bench_v1.{json,md} + poc4_e2e_v1.json + acceptance_v1.json.

### Expected Result

If the hypothesis held: F=12 end-to-end speedup ≥5× (vs best-free, incl. transfer and merge); single-op ≥2×. Preregistered failure criteria: <2× → STOP; ≥2× but <5× → record negative result NRR-2026-024.

### Actual Result

E2E F=12 end-to-end speedup 3.035–3.046× (committed poc4_e2e_v1.json 3.0353×; Phase 4 fresh round 3.046×, arm order rotated eliminating the fixed-order thermal bias; cross-run delta 0.34% stable). The ≥2× minimum acceptable was met (PASS-partial); the ≥5× preregistered target was NOT met (hypothesis falsified). Single-op (binding level incl. transfer, corpus_synth_v1 full, vs best-free): all ops below 5× except factor_corr ~12–15× (≥5×, binding level); cs_rank/parameter_scan/rolling_ic/stock_corr general observed in the 1.6–3.8× range. ⚠️ CROSS-SESSION VARIANCE DISCLOSED: single-op medians on this RTX 4060 Laptop vary up to ~2× across sessions (e.g. cs_rank 1.6×→3.1×, cupy baseline 69ms→218ms); per-op boundary claims (e.g. cs_rank <2×) are NOT cross-session stable and are indicative only; the E2E criterion (preregistered decision) is stable. Component-level negative surfaced: e2e per-op ic_stack (IC merge) ~0.72× worse than baseline, never buried. Key layer finding: earlier acceptance below_5x (cs_rank 3.01×/parameter_scan 3.02×/rolling_ic 3.14×) were kernel-resident (GPU compute only, transfers excluded); user-facing (binding incl. transfer) is lower; adapter factor_corr f32→f64 Python upcast adds +178%~+266% (product-level factor_corr ~3.98× <5×; binding 12–15×). corpus_real_v1 (N=93) correctness + bitwise-determinism anchor only.

### Why Did It Fail?

The preregistered ≥5× end-to-end target was not met (3.04×); the ≥2× minimum was met. Attribution is per-mechanism, each labeled CANDIDATE rather than confirmed: ① FP64 hardware ceiling (candidate, no FP32-aggregation confirmatory experiment run) — RTX 4060 Laptop FP64 ≈ FP32/64 may cap the float64 aggregation ops (rolling_ic/factor_corr reductions/stock_corr general), BUT the same-evidence factor_corr (float64) reaches 12–15×, weakening the ceiling as the main cause. ② Launch/transfer/occupancy overhead (candidate) — explains the float32 ops (cs_rank/parameter_scan) and the product-level transfer cost. ③ Positive control (binding level) proves kernels CAN reach ≥5× — factor_corr 12–15× on the same non-degenerate corpus_synth_v1 panel; below_5x is workload/layer-related, not universal kernel inefficiency. ④ Kernel-resident reporting overstates the user side — the acceptance numbers were GPU-compute-only; the product (incl. transfer) pays more. ⑤ Adapter Python overhead — the contract-mandated f32→f64 Python upcast (factor_corr +178%~+266%) drops the PRODUCT-level factor_corr to ~3.98× <5×; a product-layer optimization opportunity, not a binding defect. Cross-session variance: single-op medians vary ~2× on this machine, so per-op boundary claims are not decision inputs; the decision rests on the stable E2E. Untested alternative explanations (higher-FP64 GPU, FP32 aggregation path, kernel tuning) are labeled UNTESTED HYPOTHESES. Conclusion bounded to RTX 4060 Laptop + fixed corpus + the stock_corr-excluded E2E scope.

### What Did We Learn?

- The preregistered dual threshold (≥2× minimum / ≥5× target) made 3.04× an unambiguous verdict: minimum met, target missed → honestly record the negative, never package a documented gap as success.
- Consumer GPUs (RTX 40-series) have high performance variance — single-op speedups can swing ~2× across sessions (cs_rank 1.6×→3.1×); preregistered decisions must rest on a stable end-to-end criterion, not volatile per-op boundaries.
- Perf claims must state the LAYER and transfer scope: kernel-resident (GPU compute only), binding-incl-transfer (user pays), adapter (product) differ 2–3×; the same op gives different boundary conclusions at different layers.
- "≥5× reachable" must be anchored per mechanism: binding-level factor_corr 12–15× proves kernels can exceed 5×, but the product adapter's f32→f64 Python upcast drops the product layer to ~3.98× — report product and kernel layers separately.
- Declare and stick to the E2E adjudication scope before running (verdict_scope excludes stock_corr); surface component-level negatives (ic_stack 0.72×); benchmarks must rotate arm order + record thermal to avoid fixed-order bias.

## Key Lessons

1. **Dual preregistered threshold made 3.04× an unambiguous verdict** — minimum met, target missed → honest negative, no success-washing.
2. **Consumer RTX 40-series variance is high** — single-op speedups swing ~2× across sessions; decisions rest on the stable E2E.
3. **Perf claims must state the layer/transfer scope** — kernel-resident vs binding-incl-transfer vs adapter differ 2–3×.
4. **"≥5× reachable" must be anchored per mechanism** — binding factor_corr 12–15×; product adapter ~3.98× (Python upcast overhead).
5. **Declare E2E scope upfront; surface component negatives; rotate arm order + record thermal.**
