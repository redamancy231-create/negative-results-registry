## Experiment Overview

### Original Hypothesis

Preregistered (CLAUDE.md "PoC decision table": NRR threshold ≥5×, minimum acceptable ≥2×; PLAN.md §9): on an RTX 4060 Laptop GPU (sm_89), the fc adapter (pybind11 + CUDA) on the fixed corpus_synth_v1 (T=1218×N=5000×F=12) minimal parameter-scan pipeline (parameter_scan → per-factor rolling_ic → factor_corr + IC merge, verdict_scope EXCLUDING stock_corr) would achieve an end-to-end speedup of ≥5× versus the best free alternative (qgplearn NOT installed → min(numpy, cupy), same data/mask/semantics, including H2D transfer and merge).

### Method

Preregistration anchor: CLAUDE.md PoC decision table (≥5× NRR threshold / ≥2× minimum) and PLAN.md §9. End-to-end: benchmarks/poc4_e2e_v1.py (F∈{4,8,12} minimal parameter-scan pipeline, GPU arm via pybind bindings, numpy/cupy arms via benchmarks/backends.py, symmetric reps, verdict_scope excludes stock_corr, best_free=min(numpy,cupy) recorded at runtime); Phase 4 added a fresh round + cross-run stability gate. Single-op (product layer): benchmarks/phase4_bench_v1.py — binding level (includes H2D transfer + D2H, same layer as e2e) vs numpy/cupy best-free, median + bootstrap 95% CI (1000 resamples, seed=0) + CV, warm 3 + 20 samples, per-block nvidia-smi thermal sampling, corpus_synth_v1 full. Reproducibility: both corpora verified via corpus_loader_v1 (data_sha256 fail-closed); pipeline outputs bitwise-identical across two runs; git HEAD pinned + evidence self-hash; corpus_real_v1 (N=93) correctness/determinism anchor only, produces no perf numbers. Evidence: benchmarks/results/phase4_bench_v1.{json,md} + poc4_e2e_v1.json + acceptance_v1.json.

### Expected Result

If the hypothesis held: F=12 end-to-end speedup ≥5× (vs best-free, incl. transfer and merge); single-op ≥2×; float64 aggregation ops (rolling_ic/factor_corr) expected to contribute the main acceleration. Preregistered failure criteria: <2× → STOP; ≥2× but <5× → record negative result NRR-2026-024.

### Actual Result

E2E F=12 end-to-end speedup ~3.03–3.20× (committed poc4_e2e_v1.json records 3.0353×; Phase 4 fresh round 3.198× / 3.141× across runs, cross-run |Δmedian| ≈ 2–5% stable). The ≥2× minimum acceptable was met (PASS); the ≥5× preregistered target was NOT met. Single-op (binding level incl. transfer, corpus_synth_v1 full, vs best-free=min(numpy,cupy)): cs_rank ~1.6× (below the 2× product-level minimum), parameter_scan(G=4) ~2.2×, rolling_ic ~2.1×, factor_corr ~15× (≥5× PASS), stock_corr general N=500 ~2.1× / N=2000 ~2.6×. Component-level negative: the e2e per-op ic_stack (IC merge) is ~0.72× — worse than baseline — surfaced explicitly, never buried in the aggregate PASS. Key layer finding: the earlier acceptance below_5x numbers (cs_rank 3.01×/parameter_scan 3.02×/rolling_ic 3.14×) were kernel-resident (GPU compute only, transfers excluded); the user-facing product (binding incl. transfer) is lower, with cs_rank below 2×. corpus_real_v1 (N=93) correctness + bitwise-determinism anchor only (pipeline outputs bitwise-identical across runs), no perf numbers.

### Why Did It Fail?

The preregistered ≥5× end-to-end target was not met (~3.0×); the ≥2× minimum was met. Attribution is per-mechanism, not a single blanket cause: ① FP64 hardware ceiling (primary, explains ONLY the float64 aggregation ops) — RTX 4060 Laptop FP64 ≈ FP32/64 (official architectural limit); rolling_ic ~2.1×, stock_corr general ~2.1–2.6×, and factor_corr reductions are limited. ② Launch/transfer/occupancy overhead (explains the float32 ops + the product-level gap) — cs_rank ~1.6× and parameter_scan ~2.2× are NOT explained by the FP64 ceiling; mechanism is per-call H2D/D2H transfer + kernel launch + small-panel occupancy. ③ Positive control proves kernels are not universally inefficient — on the same evidence set, same corpus_synth_v1 non-degenerate panel, factor_corr ~13–15× (≥5× PASS) shows the same kernels CAN exceed 5×; below_5x is workload/hardware-related, not universal kernel inefficiency. ④ Kernel-resident reporting overstates the user side — the acceptance below_5x numbers were GPU-compute-only; the product (incl. transfer) pays more. Perf claims must state the transfer layer. ⑤ Adapter Python overhead — the fc adapter performs a contract-mandated f32→f64 Python upcast (~1 s/call, ~+178% vs the binding's faster internal forcecast upcast); a product Python-layer optimization opportunity, not a binding defect. Untested alternative explanations (higher-FP64 GPU, FP32 aggregation path, kernel tuning) are labeled UNTESTED HYPOTHESES, not feasibility claims. Conclusion is bounded to RTX 4060 Laptop + fixed corpus (synth_v1 scale; real_v1 correctness only) + the stock_corr-excluded E2E scope; not generalized to other GPUs or workloads not dominated by FP64.

### What Did We Learn?

- The preregistered dual threshold (≥2× minimum / ≥5× target) made ~3.0× an unambiguous verdict: minimum met, target missed → honestly record the negative, never package a documented gap as success.
- Consumer GPUs (RTX 40-series) FP64 ≈ FP32/64 is a hard ceiling for float64-aggregation workloads — check the device FP64 spec before setting a ≥5× target, or design an FP32 aggregation path.
- Perf claims must state the transfer layer: kernel-resident (GPU compute only) vs binding-incl-transfer (what a user pays) can differ 2–3× (cs_rank 3.01× vs 1.6×) — an unlabeled "speedup" is misleading.
- Hardware-ceiling attribution must be per-mechanism + anchored by a same-evidence-set positive control: FP64 ceiling explains only the float64 ops; float32 <2× is launch/transfer/occupancy; factor_corr ~13–15× proves kernels CAN exceed 5×.
- Declare and stick to the E2E adjudication scope before running (verdict_scope excludes stock_corr); surface component-level negatives (ic_stack 0.72×) explicitly, never buried in the aggregate PASS.

## Key Lessons

1. **Dual preregistered threshold made ~3.0× an unambiguous verdict** — minimum met, target missed → honest negative, no success-washing.
2. **FP64 ≈ FP32/64 on consumer RTX 40-series is a hard ceiling for float64 aggregation** — check device FP64 spec before setting ≥5×, or design an FP32 path.
3. **Perf claims must state the transfer layer** — kernel-resident vs binding-incl-transfer differ 2–3× (cs_rank 3.01× vs 1.6×).
4. **Hardware attribution per-mechanism + same-evidence positive control** — FP64 ceiling only for float64 ops; factor_corr ~13–15× proves kernels can exceed 5×.
5. **Declare E2E scope upfront; surface component negatives** (ic_stack 0.72×), never bury them.
