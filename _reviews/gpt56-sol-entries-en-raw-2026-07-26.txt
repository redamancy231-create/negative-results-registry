---

## Experiment Overview

### Original Hypothesis

> Structuring a code-review prompt into three stages—prep (loading specifications), exec (reviewing files one by one), and post (cross-checking)—was expected to improve the quality of GPT-5.5 findings in multi-file code review relative to a single-block baseline prompt that reviewed all specifications and all files together.

### Method

Prompt-TDD controlled experiment design:
- **Experimental group**: three-stage prep/exec/post prompt (A2 variant)
- **Control group**: single-block comprehensive prompt (A2 baseline)
- **Task**: review the same codebase across multiple files and record the number of findings, severity, and false-positive rate
- **Sample size**: n=24/arm
- **Cross-model replication**: primary experiment with GPT-5.5 plus independent replication with Qwen3.7-Max
- **Evaluation**: blinded evaluation by two LLMs using separate backends (reviewers did not know which group was experimental)

### Expected Result

> The three-stage prompt should produce more high-quality findings and fewer false positives. Expected effect size: d ≥ 0.3 (small to medium).

### Actual Result

The two groups showed no significant differences in the number of findings, severity distribution, or false-positive rate.

| Metric | Value |
|------|------|
| Effect size | d ≈ 0.03 (trivial) |
| Sample size | n=24/arm × replication with 2 models |
| Models used | GPT-5.5, Qwen3.7-Max |
| Replication consistency | Qwen replication Δ = −0.014, directionally consistent (both null) |

---

## Interpretation and Reflection

### Why Did It Fail?

The most likely explanation is that **the task type determines the upper bound on the effect size of prompt variations**. Code review is a structured classification task: the reviewer checks explicit specifications item by item. In such tasks, prompt “packaging” (segmented versus single-block) has much less influence on output quality than the constraints imposed by the task itself. Put differently, when the specifications are sufficiently explicit, how the prompt is written matters much less.

### What Did We Learn?

1. **Prompt-variation effects are near zero on structured classification tasks**—unlike open-ended generation tasks such as translation and writing, where prompt variations have larger effects
2. **The specification itself matters more than prompt structure**—invest effort in writing strong review criteria rather than organizing prompt paragraphs
3. **Negative results require cross-model replication**—the null effect with GPT-5.5 could have been single-model noise; the Qwen replication confirmed that the effect was indeed null
4. **Separating the experiment's “engineering gate” from its “scientific gate” is valuable**—even with a negative result, the experimental structure itself remains reusable
5. **Effect sizes should be estimated with a ceiling probe before the experiment**—had the ceiling effect for structured classification been known, expectations for this direction would likely have been lower

## Experiment Overview

### Original Hypothesis

> Declarative action routing (defining available actions in YAML/JSON → exact matching) was expected to outperform natural-language routing (describing available actions in natural language → semantic matching), because the declarative format reduces room for ambiguous LLM interpretation of action semantics.

### Method

Prompt-TDD controlled experiment design (pilot stage):
- **Experimental group**: declarative action-routing prompt (actions defined in YAML, strict matching)
- **Control group**: natural-language routing prompt (actions described in natural language, semantic matching)
- **Task**: a Claude Code agent autonomously selected actions during multi-step tasks (file operations, search, execution, and so on)
- **Sample size**: 15 pilot cases (experimental-design stage—Tier 0; did not proceed to Tier 1 inferential statistics)
- **Evaluation**: routing accuracy + task-completion rate

### Expected Result

> Declarative routing should reduce action-selection errors, with an expected improvement in routing accuracy of ≥10%.

### Actual Result

Across the 15 pilot cases, the two groups showed no significant difference in routing accuracy or task-completion rate. The effect size was insufficient to justify proceeding to a full-scale Tier 1 experiment.

| Metric | Value |
|------|------|

| Sample size | 15 cases (pilot) |
| Models used | GPT-5.5 (via Codex CLI) |

---

## Interpretation and Reflection

### Why Did It Fail?

Two possible explanations:
1. **The LLM was already a sufficiently capable semantic router**—when actions were described in natural language, the LLM's semantic understanding was sufficient to resolve ambiguity, making the extra precision of the declarative format redundant
2. **The pilot sample was too small**—15 cases may have been insufficient to detect a small effect. But the purpose of the pilot was precisely to determine at low cost whether a full-scale experiment was worth the investment; the answer was “no”

### What Did We Learn?

1. **The intuition that “format equals precision” is only partly correct**—declarative formats outperform natural language in conventional programming, but an LLM acting as a semantic engine may process natural language more naturally
2. **A pilot's value lies in stopping losses early**—15 cases were enough to decide against Tier 1, saving approximately 4 hours of experiment execution and 2 hours of review time
3. **A negative pilot is still a success**—A3 was labeled in the methodology handbook as a **counterexample case** showing how to close an experiment with no signal; this teaching value is more distinctive than a positive result
4. **Consistency with A2 is noteworthy but does not establish a domain-level conclusion**—A2 (n=24 controlled) and A3 (n=15 pilot) each detected no difference under their respective conditions, creating a meta-hypothesis for future testing; an aggregate study would require preregistration, multiple tasks, and adequate power before drawing a general conclusion

### Method

### Actual Result

## Interpretation and Reflection

### Why Did It Fail?

Three systemic problems compounded one another:
1. **Sample homogeneity**: the same operator extracted and reviewed every project. Although the source projects spanned different domains (quantitative finance, code review, and document generation), their level of methodological self-awareness was highly correlated through the operator; there was no independent “control sample”
2. **n=22 was too small**: extracting cross-project patterns requires a sample far larger than 22, especially when projects differ substantially (some contain tens of thousands of lines of code; others are documentation only)
3. **The stability threshold was too strict**: ≥3 sources may be too demanding for methodology-literature extraction; cross-study pattern extraction in academic literature commonly requires 30–50 papers

### What Did We Learn?

1. **Methodology extraction is an order of magnitude harder than expected**—22 projects looks substantial but is nowhere near enough
2. **Operator independence is the bottleneck**—when one person extracts every source project, that person's cognitive preferences systematically constrain pattern discovery
3. **“Could not extract” and “does not exist” are different claims**—zero qualifying patterns from 22 projects does not mean no extractable patterns exist; the method may be inadequate
4. **The process was more valuable than the result**—the review chain (33 nonoverlapping findings across two rounds plus evidence of convergence across four backends) had greater scholarly value than the framework's output
5. **An honest negative result has independent value**—the project's central deliverable shifted from a “methodology extraction framework” to an “honest report on how difficult this problem is”

# NRR-2026-004: mmdc-rendered PNG lacked DPI metadata → python-docx defaulted to 72 DPI, stretching the image ~4×

## Basic Information

| Field | Content |
|------|------|
| **Entry ID** | NRR-2026-004 |
| **Title** | mermaid-cli rendered PNGs without DPI metadata, causing python-docx to default to 72 DPI and stretch/crop images by ~4× |
| **Domain** | document-generation |
| **Category** | methodology-failure |
| **Submitter** | Acerolaorion |
| **Source Project** | docx-pipeline |
| **Source Authors** | Acerolaorion |
| **Analyst** | Acerolaorion |
| **Date** | 2026-06-23 |

---

## Experiment Overview

### Original Hypothesis

> mermaid-cli (mmdc) is the de facto standard tool for rendering Mermaid diagrams, so its PNG output was expected to be directly embeddable in a python-docx → DOCX pipeline without additional DPI post-processing.

### Method

Mermaid → DOCX pipeline in the DOCX Pipeline project (an issue discovered in an AI-assisted development environment):
1. Detect ` ```mermaid ` code blocks in Markdown
2. Calculate pixel width from the configured DPI (300 by default) → invoke `mmdc --width <px>` to render a PNG
3. Embed the PNG in DOCX with python-docx v1.2.0 `add_picture()`
4. Open the document in Word and visually verify the result

### Expected Result

> The PNG should be embedded at the intended size (approximately 80–100% of page width) and display normally in Word.

### Actual Result

The PNG appeared **stretched by ~4×** in the DOCX, extending beyond the page boundary and being cropped. Root-cause chain:

1. **PNGs rendered by mmdc contain no DPI metadata** (mmdc has no `--dpi` option; `--width` controls only rendered width and does not write the PNG pHYs chunk)
2. **python-docx calculates the embedded dimensions of an image without DPI metadata using a 72 DPI default** (not Word's 96 DPI screen density—python-docx writes explicit EMU dimensions, which Word uses directly)
3. A pixel image prepared at 300 DPI ÷ dimensions calculated at 72 DPI → physical dimensions expand by ~4.17× (300/72)

| Metric | Value |
|------|------|
| Effect size | Physical dimensions expanded by ~4.17× (300 DPI pixels ÷ python-docx 72 DPI default) |
| Sample size | Every DOCX document containing Mermaid diagrams (100% reproducible early in the project) |
| Tools used | mermaid-cli (mmdc), python-docx v1.2.0, Microsoft Word |

---

## Interpretation and Reflection

### Why Did It Fail?

**Implicit assumptions in adjacent layers of the toolchain's interoperability contract were incompatible.** This was not a single-point bug in either tool: mmdc correctly rendered the requested pixel width (`--width` controls rendered width), and python-docx correctly used its 72 DPI default to calculate the embedded dimensions of an image without metadata. The problem was the missing DPI-injection step in the contract between the two tools, while the pipeline designer assumed “mmdc PNG output = directly embeddable by python-docx.” This was a pipeline-design methodology problem, not a question of whether either individual tool was fit for purpose.

### What Did We Learn?

1. **Every stage of a toolchain requires end-to-end validation of interoperability assumptions**—the default assumption that “A's output equals B's input” must be verified for every new combination of tools
2. **Visual verification cannot be skipped**—code review alone cannot detect missing DPI metadata; the final rendering must be opened in Word and inspected
3. **Implicit defaults are breeding grounds for integration bugs**—mmdc omitting the pHYs chunk and python-docx defaulting to 72 DPI are each individually reasonable, but their combination creates a bug
4. **The fix required only one line of Pillow code**—`image.save(path, dpi=(300,300))`; however, diagnosis depended on visual inspection rather than code review, so the cost of discovery far exceeded the cost of repair

# NRR-2026-005: Amdahl's Law — 53× C++ speedup collapsed to 2.2× in batch workloads

## Basic Information

| Field | Content |
|------|------|
| **Entry ID** | NRR-2026-005 |
| **Title** | 53× C++ speedup collapsed to 2.2× in batch workloads—Amdahl's Law fixed the end-to-end speedup ceiling at ~2.25× |
| **Domain** | tool-building |
| **Category** | ceiling-effect |
| **Submitter** | Acerolaorion |
| **Source Project** | etf-pattern-match-pybind11 |
| **Source Authors** | Acerolaorion |
| **Analyst** | Acerolaorion |
| **Date** | 2026-07-12 |

---

## Experiment Overview

### Original Hypothesis

> After accelerating the pure-compute core of a pattern-matching ETF strategy with pybind11 + C++20, batch workloads were expected to achieve end-to-end speedups close to those of individual calls (expected: 10–30×).

### Method

The pure-compute Python core (DTW, pattern matching, and technical indicators) was migrated to C++ and exposed through pybind11. Measurements compared (a) individual Python versus C++ calls, (b) Python versus C++ batch processing at 100 time points, and (c) 100 individual C++ calls versus one C++ batch call. Pure-compute modules were extracted from V3.3.py (3,836 lines), excluding functions dependent on sklearn/scipy/pandas.

### Expected Result

> Individual DTW calls ≥10×, individual pattern-matching calls ≥30×, and batch end-to-end performance ≥10×.

### Actual Result

Individual DTW calls achieved 34× and individual pattern-matching calls achieved 53×, both exceeding expectations. However, **batch end-to-end performance improved by only 2.2×**—far below the per-call speedup. Root cause: only **~56% of the batch workload was accelerable** (p≈0.556), while 44% was serial overhead. The theoretical speedup ceiling was 1/(1-p)≈2.25×; the measured 2.2× was already near that ceiling.

| Metric | Value |
|------|------|
| Effect size | Individual call 53× → batch 2.2× (24× attenuation); theoretical ceiling ≈2.25× |
| Sample size | 100 warm-up runs + median of 100 timed runs × 6 functions |
| Serial fraction | 44% (Python loops 15% + data conversion 15% + pybind11 calls 8% + feature computation 6%) |
| Models used | DeepSeek-V4-Pro, Kimi-K2.7-Code |

---

## Interpretation and Reflection

### Why Did It Fail?

**This is a textbook example of Amdahl's Law.** The 53× per-call speedup was not “wrong”—both 53× and 2.2× were accurate measurements of different things. The 53× figure measured the pure-compute hot path (14.0 ms→0.26 ms); 2.2× measured end-to-end batch throughput (50 ms→23 ms, including non-accelerable orchestration, data movement, and Python/C++ boundary overhead). This was not a bug; it was an architectural ceiling.

### What Did We Learn?

1. **Amdahl's Law is not a theoretical abstraction**—the measured 2.2× versus a 2.25× ceiling shows that mathematical modeling closely matched real measurements in a quantitative-computing workload
2. **“Per-call speedup” and “end-to-end speedup” are entirely different metrics**—the former describes computational efficiency; the latter describes throughput improvement visible to the user
3. **The 44% serial overhead was decomposed precisely into four categories** (loops/conversion/calls/features), each requiring a different optimization strategy
4. **Achieving 10× end-to-end requires 92% of the workload to be accelerable**—architectural restructuring may be more fundamental than further C++ migration

### What Did We Learn?

1. **The same AI or operator should not simultaneously serve as designer, executor, verifier, and scorekeeper**—the Phase 4 self-assessment in the M&A pipeline violated its own five iron rules
2. **Self-assessment “highlights” can systematically become critical defects under independent blind review**—none of the three self-identified highlights (data reconciliation, CAR, and DuPont) survived
3. **Optimistic self-assessment bias is not an isolated case**—the ~11% bias recorded in `methodology-handbook` reappeared here in an extreme 36.8-point form
4. **Three critical defects were diagnosed repeatedly but never fixed (Phase 9 never ran)**—a diagnosis that is not implemented is a diagnosis wasted

2. **The three blind spots share one feature**: the bugs occur not in source-code logic but in implicit interaction contracts between adjacent tools

## Experiment Overview

### Original Hypothesis

> The three-artifact synchronization protocol—.md (authoritative source) → .json + .docx—should guarantee content consistency across the three formats. A PASS at the version gate (O6) should mean that the three artifacts are consistent.

### Method

Before the release of AI collaboration framework v1.6.4, the O6 version gate (`verify_version_consistency.py`) was run. Codex (GPT-5.5) then performed a cross-backend review of the three artifacts, comparing content consistency chapter by chapter.

### Expected Result

> The three artifacts should be fully content-consistent and the version gate should PASS.

### Actual Result

The version gate PASSED (the version number “1.6.4” matched across all three files). However, Codex's content-level review found that **.json omitted prose revisions from .md** (wording corrections, explanatory paragraphs, and so on), while .docx included those revisions automatically through full regeneration. Root cause: .json used point patches (manually patching an old JSON version), whereas .docx used full regeneration (pandoc generated it from the latest .md). During a cross-session handoff, the point-patch maintainer did not know about all prose changes in .md.

| Metric | Value |
|------|------|
| Effect size | Content-level inconsistency between .json and .md (undetectable by O6 version gate) |
| Sample size | One three-artifact cross-review before the v1.6.4 release |

---

## Interpretation and Reflection

### Why Did It Fail?

**A design defect in the synchronization protocol.** The O6 version gate checked only version-number consistency and could not detect content-level drift. The two derived formats used asymmetric synchronization strategies—.docx was fully regenerated (naturally preventing drift), while .json used point patches (depending on the operator knowing every change). During a cross-session handoff, the latter was bound to lag.

### What Did We Learn?

1. **Version-number consistency ≠ content consistency**—the O6 version gate PASSED even though .json and .md had prose-level drift
2. **An asymmetric synchronization strategy is a design defect**—point patches versus full regeneration will inevitably be exposed during cross-session handoffs
3. **Point patches assume that the operator knows every change in .md**—this assumption fails in multi-session handoff scenarios
4. **The definitive fix is to regenerate everything from .md**—eliminate every manual synchronization path

## Experiment Overview

### Original Hypothesis

> Introducing multiple LLM backends into AI coding systems for cross-review and self-correction was expected to produce genuinely independent verification: reviewers' findings should be highly complementary, and the panel as a whole should outperform any single model.

### Method

CrossCheck (sburl/CrossCheck, a multi-model AI coding autonomous-loop system) was analyzed methodologically, with cross-validation against Kohli (2026-05) on quantified independence in a panel of nine frontier LLMs and Kuai et al. (2026-04) on behavioral entanglement among 18 LLMs. This project's two-round Phase 5 review (GPT-5.5 + Qwen3.7-Max) provided comparison data.

### Expected Result

> A panel of models using different backends should provide close to N independent perspectives; the expected number of effectively independent votes was ≥5 out of 9 models.

### Actual Result

Kohli (2026-05): **A panel of nine frontier LLMs had only ~2 effectively independent votes. A single best judge matched or even exceeded the performance of the full panel.** This project's Phase 5 review produced 17 findings from GPT-5.5 + 16 from Qwen3.7-Max = 33 findings with zero overlap—complementary, but also suggestive of diminishing returns. | Metric | Value |

## Interpretation and Reflection

### Why Did It Fail?

This does not mean multi-model review is ineffective—quite the opposite: 33 findings with zero overlap demonstrate complementarity. However, shared training data, distillation, and alignment pipelines create implicit dependencies between models, so the marginal benefit of “adding more models” drops sharply after approximately 2–3 effectively independent perspectives. Four or five models from different providers may already be close to the effective ceiling.

### What Did We Learn?

1. **A nine-LLM review panel yielded only ~2 effectively independent votes**—shared training data and evaluation benchmarks create implicit dependencies between models
2. **The value of multi-model review is concentrated in the first 2–3 models from different providers**—marginal returns drop sharply afterward
3. **“Different CLI houses” ≠ “independent”**—models from different companies may still share training data and benchmarks
4. **The empirical value of multi-model review is finding complementary blind spots** (33 findings with zero overlap), not claiming that all views are independent

2. Phase 5's 33 findings with zero overlap were not “models arguing”—they reflected different error sensitivities and complementary coverage of blind spots
3. “High inter-model agreement = high quality” is a hypothesis that requires testing—agreement can also reflect a shared blind spot

This ceiling was not caused by insufficient analytical depth; it was imposed by the information capacity of the source project itself.

### What Did We Learn?

1. Methodology extraction from minimal projects has an inherent ceiling—the smaller the source project, the harder it is for the evidence grade to exceed [Sp]
2. N=2 evidence has only directional-indication value—it cannot carry the weight of [E]-level evidence
3. A 100-line core is both a methodological strength and an extraction limitation—it cannot provide evidence of diversity
4. For small external projects, set an evidence-grade ceiling in advance—avoid discovering only after three analysis rounds that everything is [Sp]

## Experiment Overview

### Original Hypothesis

> The methodology-extraction framework should be able to extract meaningful methodology patterns from unknown open-source projects—even when a project has no AI collaboration records, usable signals should be extractable from passive traces. The expected minimum gradient (a pure-code project) had an extraction rate of ≥50%.

### Method

A complete eight-component extraction was performed across three project gradients: own projects (★★★★★), ml-quant-trading (★★★, with paper + CI + tests), and NPGS (★, with zero methodology documentation).

### Expected Result

> Extraction rates should decline progressively across the three gradients while retaining a baseline—NPGS ≥50% (4/8).

### Actual Result

**The gradient was 100% → 69% → 37.5%.** Five of eight NPGS components were blank. The three extractable components could also be obtained with GitNexus, meaning the framework had **no incremental value** for passive traces.

| Metric | Value |
|------|------|

| Sample size | 3 projects × 3 gradients × 8 components |
| Models used | DeepSeek-V4-Pro, GitNexus, Codex GPT-5.5 |

---

## Interpretation and Reflection

### Why Did It Fail?

The framework's implicit assumption—“the source project knows what it did and recorded it”—does not hold for most open-source projects. The framework is not a “detector” but an “organizer”: it cannot discover information that does not exist.

### What Did We Learn?

1. The framework's applicable population is extremely narrow—it works only for projects with very strong AI-collaboration self-awareness
2. Extraction rate is positively associated with the source project's methodological self-awareness (★★★★★=100%→★=37.5%)
3. The framework has no incremental value for passive traces—anything GitNexus can obtain does not require the framework
4. The framework's value proposition should be corrected from “discovery” to “synthesis”—it is not a detector but an organizer

# NRR-2026-022: Extractor contamination created a false methodology signal

## Basic Information

| Field | Content |
|------|------|
| **Entry ID** | NRR-2026-022 |
| **Title** | “Extractor contamination”—methodology documents added by a fork author were misattributed to the source project, creating a false methodology signal |
| **Domain** | methodology-extraction |
| **Category** | methodology-failure |
| **Submitter** | Acerolaorion |
| **Source Project** | NPGS |
| **Source Authors** | baopinshui |
| **Analyst** | Acerolaorion |
| **Date** | 2026-07-23 |

---

## Experiment Overview

### Original Hypothesis

> When extracting methodology from a fork's source project, all files in the fork repository should reflect the source project's methodological characteristics. Additional documents were expected to supplement the source project's methodology information.

### Method

A complete methodology extraction was performed on NPGS (baopinshui/NPGS). After the repository was forked, the extractor added `CLAUDE.md`, a GitNexus index, and analysis reports, then performed extraction from the fork. The documents were traced afterward to determine which came from the source author and which came from the extractor.

### Expected Result

> At least some additional documents should reflect or supplement the source project's methodological characteristics.

### Actual Result

**`CLAUDE.md`, the GitNexus index, and the analysis reports were 100% created by the fork extractor.** The source project had zero methodology documentation. Without distinguishing the two, the extractor would misattribute the “only methodology documentation written by the extractor” to the source project as evidence of “methodological self-awareness.”

| Metric | Value |
|------|------|
| Effect size | Source-project methodology documentation = 0; fork-added documents = 100% extractor-authored |
| Sample size | 1 project × comparison of extractor versus source-author documentation |
| Models used | DeepSeek-V4-Pro, GPT-5.6-Sol, GitNexus |

---

## Interpretation and Reflection

### Why Did It Fail?

A design defect in Phase 0 of the extraction framework. When the extractor is also the sole author of methodology documentation in the repository, the default assumption that “repository documentation reflects the source project” systematically overestimates the source project's methodological self-awareness.

### What Did We Learn?

1. Extractor-authored documentation ≠ source-project methodology—it creates a false signal
2. Phase 0 needs an “extractor contamination” check—down-weight documentation when its author ≠ the source project's author
3. Analysis artifacts added after forking should not be treated as source-project methodology—an observer effect
4. Zero source-project documentation is an honest signal, not an extraction failure

### Did It Succeed Later?

This is a fixable design defect: adding an extractor-contamination check to Phase 0 is sufficient to filter it out. It is not a structural framework failure.
